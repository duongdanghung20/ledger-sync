# Journal Entries are pushed idempotently, one per call, synchronously

Approved Journal Entries post to a Book's QuickBooks company one at a time via `POST /v3/company/{realmId}/journalentry` (not the `batch` endpoint), synchronously within the push request (no background worker). Each Journal Entry carries a stable `requestid` (a UUID minted when the entry is approved, persisted, and never regenerated) plus a stable `DocNumber` derived from the entry's id; on an ambiguous failure (5xx, network, or timeout) we query QuickBooks by `DocNumber` before any retry, and on a 429 we stop the push rather than sleep inside the request. We picked this because the correctness bar on the money path is that a retry must never double-post: QuickBooks' native `requestid` replay guarantees that for prompt retries, and query-before-retry closes the gap for delayed retries and for a crash mid-push (the entry stays `pending` and is reconciled on the next push, never duplicated). Single-call and synchronous was chosen over the batch endpoint and a job queue because v1 volume — one Bookkeeper, hundreds of entries — sits well inside the 500/min and 120s-request budgets, and both alternatives add real cost for no v1 benefit: batch replay requires matching both the `requestid` and each per-item `bId`, and a worker adds a broker to the deployment. The trade-off is that a very large push (thousands of entries in one session) could exceed a single request's budget; accepted for v1, revisited by moving to the batch endpoint and/or a background worker if volume demands it.
